# Phase 2 Pre-Merge Token Cleanup

Deferred cleanup run before merging `phase-2/input-underline-pilot` into `main`.
Items here were intentionally left alone during Pilots 1–4 to avoid mid-pilot
scope creep. Every removal below was confirmed zero-consumer by a read-only
audit first — grep for the Tailwind utility **and** a `var(--x)` usage count in
the compiled bundle, since a CSS variable can be declared and emitted while
nothing consumes it.

Not a pilot; no design decisions were made here. Nothing was renamed or
remapped — only dead surface area removed.

---

## What was removed

### 1. `--input` (shadcn alias)

| Was | Location |
|---|---|
| `--input: var(--border);` | `globals.css:152` |
| `input: "rgb(var(--input) / <alpha-value>)",` | `tailwind.config.js:71` |

Zero consumers: `border-input` / `bg-input` / `text-input` appeared nowhere in
the codebase, and `var(--input)` appeared **0** times in the compiled CSS.

⚠️ **Not to be confused with `--input-underline`** (`globals.css:33`), which is
live and load-bearing — it drives the three `shadow-underline*` keys
(`tailwind.config.js:48-50`) used by `input.tsx`, `textarea.tsx`, and
`select.tsx` from Pilot 1. A naive `grep -- "--input"` returns both; match
`--input:` / `var(--input)` exactly.

### 2. `--ring` (shadcn alias)

| Was | Location |
|---|---|
| `--ring: var(--focus-ring);` | `globals.css:153` |
| `ring: "rgb(var(--ring) / <alpha-value>)",` | `tailwind.config.js:72` |

Zero consumers: no `ring-ring` / `border-ring` / `outline-ring` anywhere, and
`var(--ring)` appeared **0** times in the compiled CSS. Every `ring-*` usage in
the app pairs `ring-2` with an explicit `ring-primary`
(`button.tsx:8`, `dialog.tsx:45`, `sheet.tsx:66`), so nothing fell through to a
default.

⚠️ **Not to be confused with `--focus-ring`** (`globals.css:88`, `#0E7C5A`
jade), which is live via `tailwind.config.js:49`.

**Known and deliberately left alone:** `ringColor.DEFAULT` is still Tailwind's
stock `#3b82f680` (blue-500/50) — it was never wired to `--ring`. A future bare
`ring-2` written without an explicit colour class will therefore render Tailwind
blue, not jade. Removing `--ring` did not create that trap, but it removed the
token that *looked* like it would prevent it. Deferred to its own ticket.

### 3. `--status-*` (Direction B teal, 4 variables)

| Was | Location |
|---|---|
| `--status`, `--status-hover`, `--status-active`, `--status-tint` | `globals.css:111-114` |
| the whole `status: { DEFAULT, hover, active, tint }` block + its decision-#30 comment | `tailwind.config.js:122-129` |

Introduced by decision #30 as a brand-new Direction B teal role and never wired
to anything. Superseded by Phase 1.1's semantic `success` / `info` / `neutral`
families, which remain untouched. Zero `.tsx` usages, `var(--status` count **0**
in the compiled CSS. `globals.css` had already self-documented it as orphaned.

Precedent: decision #29 deleted `--text-muted` in Phase 1 for the same reason.

### 4. Corrected an inaccurate comment (`globals.css:97-98`)

The comment claimed these tokens were *"still consumed by `tailwind.config.js`,
so removing them would break the build."* **That was false.** A Tailwind colour
key referencing an undefined CSS variable is not a build error, and an unused
key emits nothing at all under JIT — confirmed by this cleanup, which removed
both halves and built clean. The comment was corrected rather than silently
dropped, so anyone who read the old claim can see it retracted.

### 5. `dropdown-menu.tsx`: bare `border` → `border-border`

`dropdown-menu.tsx:48` (`DropdownMenuSubContent`) and `:66`
(`DropdownMenuContent`) were the only two places relying on the global
`* { @apply border-border }` base rule (`globals.css:156-158`) for their border
colour. Every sibling states it explicitly — `button.tsx:17`, `card.tsx:12`,
`dialog.tsx:39`, `popover.tsx:20`, `select.tsx:94`, `toast.tsx:65`.

Worth being precise about why this was not a no-op rename: `border` and
`border-border` are **different utilities** — `border` sets `border-width: 1px`
and no colour; `border-border` sets `border-color` and no width. They coincided
only because of the `*` base rule. Had that rule ever been narrowed or removed,
dropdown's borders would have silently fallen back to `currentColor` while every
other component kept its hairline.

Verified identical after the change: `DropdownMenuContent` computes
`rgb(228, 231, 236)` (`#E4E7EC` = `--border`), 1px solid — byte-identical to
`DialogContent`, which has always been explicit.

## ⚠️ shadcn generator caveat (read before `npx shadcn add`)

`components.json` sets `"cssVariables": true` and `"baseColor": "slate"`. Any
component generated by `npx shadcn add <component>` will emit **stock shadcn
classes**, including `border-input` and `ring-ring` — both of which reference
tokens that no longer exist.

**This fails silently.** Tailwind does not error on an unknown utility; it
simply emits nothing. The result is a component with no border colour and/or no
focus ring, with a green build and passing tests.

After generating any new shadcn component, replace:

| Generated | Use instead |
|---|---|
| `border-input` | `border-border` |
| `ring-ring` | `ring-primary` (jade, per decision #36) |

Also worth checking on generated components, though not caused by this cleanup:
`focus:` → `focus-visible:` (per Pilot 3/4), and `shadow-*` → `shadow-none` on
overlay/panel surfaces (per the Card/Button/Dialog precedent).
